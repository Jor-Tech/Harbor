# Desktop releases

The release pipeline publishes only to the repository where it runs; it does not change repository visibility. Release assets are separate from the 3-day CI artifacts. The public update endpoint is fixed to `Jor-Tech/Harbor`.

## Find and install an update

Open **Settings → Releases & updates** to see the running version, platform and architecture. **Check now** checks the public GitHub releases API. **Automatically check for updates** is off by default; enabling it schedules a check after 30 seconds and every 12 hours while the app is running, including in the system tray. **Include preview releases** initially follows the installed version: enabled for a preview, disabled for a stable version. Both preferences are stored locally in `updates.json`, separately from the vault and its sync settings.

Harbor compares semantic versions, including numbered alpha/beta versions, and requires a published installer for this device's operating system and architecture. Drafts and releases without a matching installer are ignored. An available newer version adds a titlebar notification; selecting it opens Settings. **Download update** downloads the selected version on Windows (NSIS) and Linux (AppImage or DEB). Progress, cancellation and retry are available in Settings. **View releases & downloads** remains available at all times for manual installation.

Requests use the public API without GitHub tokens, cookies, vault contents or host information. GitHub receives the network request, including the device's public IP address. Repeated checks share the current result for at least 60 seconds; rate limits can extend that delay. Network, private-repository and incomplete-response errors are shown as errors, never as confirmation that Harbor is up to date. If the repository is still private, use the browser link with an authorized GitHub account. A channel with no compatible releases is reported explicitly.

Downloads and installation are explicitly user initiated. A verified download changes the titlebar notice to **Update ready**. **Install and restart** asks for confirmation before closing terminals, transfers and MCP connections. Pending vault writes finish before installation; saved vault data and local MCP settings remain in the existing data directory. Windows runs the NSIS installer, AppImage replaces the running image, and DEB asks the system permission agent (`pkexec`) to install the downloaded package with `dpkg`. A cancelled or failed DEB installation keeps Harbor open and allows retry. No automatic package-repair commands run. Normal app exit never installs a downloaded update. **Dismiss update** clears the ready state; verified files may remain in the updater cache and be reused after a future check.

The download uses a public HTTPS feed pinned to the exact selected GitHub release tag, with no GitHub tokens or user-provided URL. Harbor requires the expected version, platform filenames, sizes and SHA-512 hashes before downloading; `electron-updater` validates the downloaded bytes. Full downloads are used; differential block maps are not required. Release-channel changes and further checks pause while an update is downloading, ready or installing. Disabling automatic checks still stops the checker timer and pending API check; it does not cancel an explicitly requested download (use **Cancel download**).

Current macOS builds are ad-hoc signed, so direct installation is disabled there: Squirrel requires publisher signing. Development and unsupported package formats also keep the manual route. Old releases without the new update metadata report a download error with the manual alternative. Users on an older Harbor version must install the first build containing this feature manually; subsequent supported releases can be installed from Settings. Download readiness is not restored after restarting Harbor; checking and downloading again can reuse verified cache files.

For a manual update, quit the running app, install the new package, reopen it, and confirm the version in Settings. Export an encrypted backup from **Vault & sync** when a separate recovery copy is desired. Keep the same Harbor data directory; app replacement and vault import are different operations. The existing data paths, application ID and vault format are unchanged.

## What’s new in the installed version

**Settings → Releases & updates → What’s new** opens short, offline release highlights with older versions expandable. The **Show what’s new after updates** switch is on by default and independent of network update checks. Its value and the last acknowledged version are stored only in `whats-new.json` in the device’s Harbor data directory; they are never synced with the vault.

After a meaningful update, the overview opens once after unlocking, when the app is focused and idle and no other dialog is open. It combines skipped releases into one overview. Routine maintenance releases only add a **New** badge in Settings. Reading the overview marks the installed version as seen, including when opened manually. Closing it works with **Get started**, the close button or Escape. Turning automatic display off keeps the manual history available.

The first launch with this feature establishes a baseline without showing historical announcements, including when upgrading from a build that did not track viewed releases. Development builds do not automatically show highlights or establish that baseline. Downgrades do not reset the last acknowledged version.

`npm run test:whats-new-ui` covers installed-app behavior using an isolated fixture profile, including modal priority, restart persistence, opt-out, maintenance releases, first use and narrow/light/dark layouts. It is also included in the source and packaged desktop suites.

## Publish a version

1. Update `package.json` and `package-lock.json` to the same version, and add `docs/releases/<version>.md`. Include changes, installation instructions and known limitations. Also add an entry to `electron/release-notes.json`: version, release date (`YYYY-MM-DD`), short title, up to five plain-language `items`, and an explicit `meaningful` boolean. Use `true` for new user-facing features or important behavior changes, and `false` for routine maintenance. Keep older entries for the in-app history; tests require an entry for the running version. These highlights ship offline with the app, so review them before packaging.
2. Push a `release/<version>` branch and open a PR. Wait for **Linux checks**, **Secret checks**, and **Desktop previews** to pass on the latest commit. Release-branch pushes automatically build all four targets and validate the complete asset set without publishing. Other branches can start **Desktop previews** manually.
3. Merge to `main`. After checking the intended commit, create and push its exact version tag, for example `v0.4.0`. Use the normal signed-tag workflow if configured. Do not move or reuse release tags.
4. The **Desktop release** workflow rejects mismatched tags or commits outside `main`, runs the complete desktop pipeline at the tagged commit, and publishes only after all four desktop jobs and **Complete release assets** succeed. That final validation combines the real platform artifacts and checks installer names, checksums, versions and source commits.

Merging to `main` does not start another desktop build. Full platform builds run for release-branch pushes, manual previews and release tags; routine feature PRs run Linux checks and the secrets scan. A new push cancels an older preview for the same branch. A failed release build never publishes incomplete installers.

The build jobs have read-only repository permissions. Only the final publish job receives `contents: write`, using the built-in GitHub Actions token. No personal access token or publisher-signing credentials are needed. The pipeline validates all four platform manifests and all seven installers, assembles one `SHA256SUMS.txt` and `BUILDS.json`, and generates `latest.yml` (Windows) and `latest-linux.yml` from the verified installer bytes. These feeds use JSON syntax, which is valid YAML. It creates a draft, uploads the complete asset set including those feeds, and publishes it. Versions with a prerelease suffix are marked as GitHub prereleases. The client pins the generic provider to `/releases/download/<tag>/`, so previews use the same feed filenames without mixing channels or allowing downgrades. The generic publish setting also makes electron-builder embed `app-update.yml` and the DEB package identity; builds still use `--publish never`.

A failed build publishes nothing. A failed upload leaves a draft: inspect the failure, delete only that incomplete draft in GitHub (keep the tag), then rerun the failed workflow. The publisher does not overwrite an existing release or its assets. A successful published release should be corrected with a new version, never by silently replacing installers.

## Upgrade validation

Every source and packaged desktop run includes `test:release-ui`. It opens a frozen encrypted fixture written by preview.7, verifies all collections and credentials, checks that unlocking alone does not rewrite the vault, changes a setting, restarts the app, and verifies the saved data and device preferences. Wrong-password handling, fixed browser navigation, update detection, preview selection, device-only preference persistence, titlebar notification navigation, private-repository errors and compact layout are also tested. Update responses and browser navigation are stubbed; these tests never contact GitHub. Backend tests additionally cover semantic ordering, platform assets, pagination, response limits, cancellation, scheduling and rate limits. Only synthetic data is used.

On an ephemeral GitHub Linux runner, `check-linux-upgrade.cjs` additionally installs the newest available older published DEB from the recent releases listing, opens and saves the synthetic profile with that version, installs the new DEB, and checks the same profile across restart and package removal. For the first published release there is no previous DEB baseline: the job explicitly reports that it tested first installation with the preview.7 profile instead. It never runs on a developer laptop.

Update tests cover the pinned feed, metadata rejection, download failure/cancellation/retry, progress, explicit restart confirmation, installer failure, delayed writes, format support, release feed checksums and channel locking. The release UI test exercises the real IPC and UI with synthetic updater/OS boundaries, including navigation during downloads, a ready notification and permission cancellation. It never downloads or executes a real installer. End-to-end NSIS, AppImage replacement and elevated DEB updates still require representative installed devices; passing mocked flows does not establish their real installer lifecycle behavior. macOS remains a manual DMG upgrade.

## Signing and visibility

Installers are not publisher-signed (macOS ad-hoc signed, not notarized), including releases without a prerelease suffix. Checksums help detect changed bytes; they do not establish publisher identity. The update trust boundary is the fixed GitHub repository and its HTTPS release assets. OS warnings and Gatekeeper restrictions remain possible. Publisher signing and notarization remain separate work, and are prerequisites for enabling direct macOS updates. Do not disable system-wide protections to install Harbor.
