# Local MCP access

Implementation contract, checked against `0.4.0-alpha.9` on 2026-10-27. MCP is off by default and device-local; its configuration is never folder-synced with the vault. Start with the [setup and agent guide](mcp-agent-guide.md) for client configuration, tool arguments/results and an example workflow.

Harbor exposes a separate allowlisted MCP service, never the renderer's internal invoke interface. Clients cannot read or unlock the vault, export credentials, alter host identities, create tunnels, access local terminals or change their own permissions. Only explicitly selected host IDs are accessible; new hosts do not inherit access.

The local Node.js stdio bridge talks to a Unix domain socket (Linux/macOS) or local named pipe (Windows). There is no TCP/HTTP listener. The bridge verifies the paired Harbor installation's local TLS 1.3 certificate before sending any credential or MCP message. The self-signed certificate is trusted only by that client configuration; no public CA or network listener is involved. Each client has a random bearer credential in a private local file; Harbor stores only its hash. Possession of that file is the identity, not the app's self-reported name. Local malware running as the same user, an administrator, or a client deliberately forwarding its access is outside this boundary. A local transport does not prove which executable is using a credential. Protect credential files and pair only trusted clients.

Permissions and sessions are per client and per host. Commands, connections, file access and output sharing require either one-time approval or an explicitly remembered permission in Harbor. Remembered GUI permissions bind to the paired client, host ID, public SSH account/destination and jump route. Commands and file reads/listings match exact text/path by default. Only an explicit advanced GUI setting permits any command on one selected host; file writes in the GUI require one-time approval of exact content unless an explicit temporary or saved write permission matches. SSH host verification and MFA still apply. Remote text is untrusted data. An allowed command can have arbitrary effects under the SSH account; Harbor cannot infer safety from its spelling. Output can contain secrets and may be sent to a cloud model by the local client; local MCP transport does not keep already-shared output on the laptop.

Locking, disabling access, changing a policy or revoking a client invalidates sessions, pending requests and results in flight. Unlock alone does not resume access. Audit records retain bounded metadata, not commands, file paths, contents, passwords, tokens or terminal output.

Background mode retains the approval window. Fully headless mode denies interactive approvals and authentication challenges. It starts locked and accepts the vault password only from an explicitly attached local terminal, never an argument, environment variable, configuration file or MCP call. Headless execution requires separately configured unattended rules. Exact actions are the default; broader scopes and writes require explicit local configuration and consent. Command glob/prefix patterns are not supported.

Publication is gated by the native release pipeline. See [validation and device checks](validation.md) for coverage and remaining hands-on checks; source availability is not a statement that installers have been published.

## Setup and review

See [validation and device checks](validation.md). Local MCP uses the official SDK over stdio through `electron/mcp/bridge.cjs`; installed builds copy this standalone bridge to `resources/harbor-mcp.cjs`. Its Node.js runtime is supplied by the local MCP client environment (Node 24+). Harbor does not modify another app's configuration automatically.

The initial fully headless runner is `node electron/mcp/headless.cjs --data-dir <absolute-directory>` from the source checkout with installed dependencies. It shares the runtime ownership lock with the GUI and requires a local hidden TTY password prompt on each launch. It is not an unattended boot service and is not yet shipped as a standalone headless installer. GUI unlock alone never resumes MCP; explicitly launching and unlocking the headless runner authorizes starting the previously configured automation policy. Unknown/changed host keys and interactive SSH authentication requests fail closed.

The private local TLS identity is in `mcp-server-identity.json`; paired client files pin its public certificate. Missing, corrupt or expired identities fail closed. To reset one, quit Harbor, remove that identity and re-pair every client; old credential files no longer trust the new server. Settings, client hashes and automation rules are in private `mcp-access.json`; bearer files are in `mcp-clients/`; bounded metadata is in `mcp-audit.json`. These device files are outside the encrypted vault and are never exported or synchronized with it. Do not put secrets in command rules. On Windows, file permissions inherit the user profile's ACL; Unix mode checks do not establish Windows ACL isolation. Local administrators and malicious software with the same user's access can compromise this boundary. Removing the configuration while Harbor is stopped disables all previous credentials; removing a credential file alone prevents that local bridge from starting but cannot revoke copies held elsewhere. Revoke the client in Harbor to invalidate every copy.

After approval, SSH connection establishment (including key-manager approval and MFA) has a three-minute limit. Other remote actions have a 30-second execution limit, combined command output/file size is bounded to 64 KiB, directory results to 200 entries, pending approvals to 32, and tool calls to 60 per client per minute. Approval expires after two minutes. Session IDs are scoped to the client connection and are invalid after disconnect. Closing an SSH channel cannot roll back remote side effects or guarantee a detached process stopped. File writes use a temporary remote file and rename; a disconnect may leave a temporary file. Exact path rules do not sandbox remote symlinks or changes on the SSH server. If a response was already shared before revocation, Harbor cannot recall it.

In the GUI/tray app, a new pending request brings Harbor forward. Choose **Review MCP requests** or open **Settings → Local MCP access**, review the exact request and choose **Approve once**. Only then does SSH begin: approve server trust if needed, choose/unlock the key in Harbor or the password manager, then answer MFA in Harbor. Secrets are not returned to the MCP client. Configure the client tool timeout to at least 330 seconds where supported, to cover the two-minute Harbor approval window plus three-minute SSH authentication window. The client may impose a shorter timeout independently.

## Default actions and per-host permissions

Under **Clients → Hosts & actions**, **Default actions** apply to selected hosts using **Use defaults**. Each host row shows its mode and allowed-action count. **Edit actions → Custom actions** copies the current defaults once; that explicit set then replaces the defaults for this host, including an empty set that denies every action. Later default changes affect only hosts using defaults. Selecting **Use defaults** explicitly removes the override. Deselecting a host removes its override; selecting it again uses current defaults. New hosts remain unselected.

Every action is checked against the selected host’s effective permissions before requesting or reusing approval. Host and connection lists are filtered by that host’s corresponding list permission; tool discovery includes actions permitted on at least one selected host. Both GUI automatic approvals and headless rules must stay within these effective permissions. Their editors disable unavailable actions for the selected host. A command permission still permits shell commands that read or modify files; denying the dedicated file-write tool does not sandbox commands.

Saving defaults or host overrides pauses MCP, cancels requests, closes MCP SSH sessions and clears the changed client’s saved GUI/headless rules plus temporary grants. Resume explicitly and review/recreate any automatic rules. Unsaved changes stay per client while navigating within the manager.

Private MCP settings now use schema version 2. Version 1 settings load with their existing defaults and no automatic expansion; the next save writes version 2. Older Harbor builds reject version 2 rather than silently ignoring host restrictions. This changes device-local MCP settings only, not the vault format or paired credentials.

## Remembered GUI approvals

New and existing clients default to asking for each remote action. **Deny request** does not create a rule. **Approve once** authorizes only the immutable request shown. **Allow for this session** remembers that exact action for this authenticated MCP client connection; its rules exist only in memory and disappear on disconnect, vault lock, MCP pause, process exit or policy changes. A subsequent SSH connection opened by the same live MCP client can reuse a matching connection permission, but a different MCP client connection cannot borrow it.

**Always allow…** presents a confirmation before saving the exact action and permission to return its results. Rules omit transient SSH session IDs; an exact command/file rule can apply to later SSH connections to the same account/destination. There are at most 20 saved and 20 temporary rules per client. Saved rules remain after lock or restart, but take effect only after local vault unlock and explicit MCP resume. No automatic rule suppresses password-manager approval, key/passphrase prompts, MFA, unknown-host verification or changed-host-key blocking.

Under each client, **Automatic approvals** groups saved and temporary permissions by host, including hosts with no automatic permissions. Each host card opens the shared host access window. Its **Automatic approvals** section lists actions in a fixed order, with their exact command/path, bound destination and removal controls. **Disable all permissions** removes that host’s saved automatic permissions in one operation; other hosts’ and clients’ saved grants remain. As with individual changes, MCP pauses and all temporary permissions expire. Manual additions first preview the resolved SSH account/address/route; saving rejects a destination that has changed since that preview. Adding or removing rules there pauses MCP, closes sessions and discards results in flight; resume and reconnect explicitly. Saving the client's ordinary host/action permissions clears its saved GUI and headless rules and all temporary rules. The advanced **allow any command** option must be selected and explicitly acknowledged in Settings; it grants the SSH account's full command power and permission to return any output. No command safety classification, prefix matching, wildcard command matching or directory subtree grants are inferred. Exact remote paths still do not sandbox server-side symlinks.

Saved GUI rules are in the private device configuration, outside the encrypted vault, and are never synced or exported. Exact commands and paths are visible in that file; do not remember commands containing passwords or tokens. Bindings hash public server/account/route identity, never passwords or private keys. Audit metadata records whether approval was once, session, saved or headless, without the command/path itself.

GUI permissions and **Headless automation rules** share exact-rule validation but remain separate grants: neither silently authorizes the other mode. Headless rules can explicitly grant any command, folder-subtree/any-path listings and reads, and exact-path/subtree/any-path file writes. GUI read/list/write permissions can explicitly allow an exact file/folder, folder subtree or any path. Each scope applies only to its selected tool. Unmatched GUI writes require content review; session or saved approval additionally requires explicit write-scope consent. GUI rules do not add an MCP management tool; only Harbor's local trusted window can create or remove them.

## GUI navigation and paired clients

Settings shows a compact status card only. **Manage local MCP** opens a dedicated workspace with Clients, Requests, Activity and Service. Each paired client has a separate credential, explicit host/action policy and remembered-rule lists. The client rail selects one configuration at a time; unsaved host/action drafts stay separate while switching clients within this workspace and are discarded when leaving or locking it. The maximum remains 32 paired clients. Existing clients retain their permissions as defaults; no host overrides are added automatically.

**Hosts & actions** and **Automatic approvals** open the same host access window, initially selecting the corresponding section. Its fixed host/client heading and internal **Allowed actions / Automatic approvals** navigation keep the surrounding app tab unchanged. Action choices and automatic-approval fields stay in place while switching sections. The default/custom selector controls inheritance; action switches control allowed requests, and purple badges identify configured saved or temporary automatic approvals. Saving action permissions from the window applies the client’s pending host/action changes and clears its remembered rules. A **Save & configure** shortcut explicitly saves pending policy changes before configuring the selected automatic action. Closing with Cancel discards unsaved window action edits; client drafts created on the main management page are retained until saved or the manager is left.

**Client setup → Client name** changes only the paired app’s local label. Credentials, permissions, active sessions and pending approvals are retained; lists, connections and requests use the updated name.

Requests and activity can be filtered by paired client ID. Approvals show the user-assigned paired name plus a short ID, not the MCP app's self-reported name. Technical request arguments are folded; exact commands, file paths and write content remain visible before consent. The global review banner opens Requests directly without changing any permission. SSH key/MFA prompts in the GUI also display their originating paired client. Ordinary direct Harbor authentication is unchanged.


## Removing clients and clearing activity

Under **Clients → Client setup**, **Remove client** is visible without expanding a section. Confirmation removes the pairing, credential file and its saved permissions, invalidates copied credentials, pauses MCP and closes all MCP sessions. Other pairings remain saved. Historical metadata remains until cleared or displaced by the 200-event limit.

**Activity** has a **Clear client activity** button for a selected client and **Clear all activity** for the unfiltered log, each with confirmation. Clearing persists across restart, keeps other clients' records when filtered, and does not stop new logging or change access permissions. Activity management is local-window-only, requires an unlocked vault and is not an MCP tool. It does not erase client-side logs, shell history or previously shared results.

## Headless scope choices

Under **Clients → Headless**, ordinary host/action permissions still form the upper limit. No write rule exists by default. Configure each rule for one client and one host:

- Commands: **Exact command**, or explicitly enable advanced access and choose **Any command**.
- Folder listings, file reads and file writes: **Exact path**, or enable advanced access for **Folder and subfolders** / **Any path**.
- File writes authorize creating/replacing content up to the existing 64 KiB limit, rather than a particular content string. Writes may also need remote directory permissions for the temporary file and rename.

The resolved account/address/port/jump route is shown before consent. New rules bind that public identity; stale previews are rejected, and changed destinations fail matching until the rule is removed and reviewed again. Old exact-only rules retain their prior behavior until reviewed and saved; saving binds them too. Removing rules remains possible when destinations are stale or unavailable. Saving/removing rules pauses MCP and closes sessions. GUI and headless grants stay separate.

**Any command can read, write or delete remote data even when the file-write tool is disabled.** File scopes match normalized requested absolute paths using component boundaries, not wildcards. They do not sandbox symlinks or concurrent server-side changes. Actual confinement requires restricted SSH-account/server permissions. Commands, paths and destinations are private device settings outside the encrypted vault; avoid secrets in rules. All approved results may be shared with the client's AI provider. No scope bypasses host-key checks, key-manager approval, MFA, output limits or the headless automatic lock.


## Optional automatic writes in the GUI

Under **Clients → Automatic approvals**, select the host, choose **Saved**, then enable **Write file contents** (or **Add scope** for another rule). This is available only after enabling **Write remote text files** under Hosts & actions. Choose **Exact file**, **Folder and subfolders**, or explicitly enable **Advanced: allow writing to any path on this host** before selecting **Any path**. Review the client, SSH destination and path scope, then acknowledge creating/overwriting files without reviewing each write and sharing the results. These rules authorize any UTF-8 content within the existing 64 KiB limit, not a fixed payload.

The saved permission binds the selected client, host/account and jump route; it survives restart, is listed under Saved, and can be removed there. Adding/removing it pauses MCP and closes its connections. Changes to the form clear confirmation. Saved GUI rules never authorize headless actions. A pending write request offers visible **Approve once**, **Allow for this session** and **Always allow…** choices. For session or saved writes, a second review defaults to the exact file, with an optional parent-folder/subfolders scope. The user must explicitly authorize future writes with any content in that scope. Changing scope resets consent. The rule is derived from the pending request and bound to its reviewed SSH destination; saving from a pending request approves that request without pausing its connection. Temporary permissions expire when the MCP client disconnects, the vault locks or MCP pauses. Outside the configured scope, Harbor asks for exact path/content approval. Path rules do not confine remote symlinks, and Any command can already modify files via the shell. Results from in-flight writes are discarded after revocation, but completed remote changes cannot be rolled back.


## Recursive GUI file scopes and full automatic approval

Read files, list folders and write files share **Exact file/folder**, **Folder and subfolders**, and explicitly enabled **Any path** scope choices under **Automatic approvals → host → Saved**. Folder scopes cover the selected folder and every nested requested path using path-component boundaries: `/work` includes `/work/sub/file`, not `/worker/file`. Each action keeps its own permission. Request-based reads, listings and commands stay exact-only; write requests support an explicitly reviewed exact-file or parent-folder scope. Scope/path changes clear confirmation; symlinks remain subject to server behavior, not a local sandbox.

**Full Automatic Approval** is available per paired client and selected host, never globally. All six remote actions must already be allowed for that host; otherwise the card links to **Allowed actions**. A separate modal identifies the client and resolved account/address/port/jump route and requires explicit acknowledgement of arbitrary commands, all-path reads/listings/writes and sharing results. Saving validates ordinary rights, the current vault/access generation, destination binding and capacity before atomically replacing that host's saved GUI rules with six broad rules. Other hosts/clients and headless grants remain unchanged. The 20-rule client limit still applies. No partial rule set is saved on failure. The existing pause, session closure and temporary-grant expiry behavior applies.

The card shows **Active** only for a complete rule set matching the current destination. **Disable full approval** clears the host's saved GUI rules. Removing an individual rule makes full approval inactive; remaining rules keep their own effect. SSH authentication, host verification, key-manager approval and MFA are unchanged. Full approval is a local management action, never a tool exposed to MCP clients.

## Inactivity locking

**Settings → Lock when inactive** accepts 1, 5, 15, 30 or 60 minutes, or **Never** (stored as `autoLockMinutes: 0`). The default remains 15 minutes. Saving the setting immediately cancels/rearms the regular app's timer; stale activity reads cannot rearm it after locking or a newer activity update. Never disables only inactivity locking. Manual lock, OS screen lock and suspend continue to lock the vault, disconnect sessions, pause MCP and clear temporary approvals. Startup remains locked. The setting is part of the encrypted vault settings. Experimental headless retains its 1–60 minute shutdown limit and uses 15 minutes for Never.


## Experimental headless support

The Headless tab is marked **Experimental**, with an explanation above its rules. The recommended route for most users is the regular Harbor app in the system tray with Automatic approvals, especially when keys or MFA require user interaction. Headless remains an advanced option for non-interactive authentication: quit Harbor entirely, start the separate source-based process and unlock locally in a terminal. There is no built-in background service. Experimental status does not bypass authentication or weaken permissions.

MCP writes stage UTF-8 content in an exclusive temporary file beside the destination and replace it with OpenSSH `posix-rename@openssh.com`. Only an unsupported-extension response enables the standard SFTP rename fallback, after confirming the destination is absent. The fallback never deletes or truncates an existing destination. Standard rename refuses a target that appears during the check. Other extension failures are reported without retrying the mutation. Temporary files are cleaned up where the connection permits. Typed local error codes distinguish denied/expired/cancelled requests from approved execution failures; only fixed messages cross the MCP boundary and error codes are retained in Activity without remote error text.
